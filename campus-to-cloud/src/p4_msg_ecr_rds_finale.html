Chapter 9

Passing messages without shouting

9,000 Diwali orders an hour. The kitchen can make 3,000. Something has to hold the line.

SNSSQSEB

The big idea: decoupling. Parts talk through messages so a slow part can't take down the rest.

A queue turns a spike into a steady flow

Red: spiky arrivals. The queue fills up during the spike and drains afterwards. Green: the kitchen processes at a steady rate. Without the queue, the spike would hit the kitchen directly and orders would fail.

Push to many. Pull at your pace.

SNS pushes a copy to every subscriber immediately. SQS stores messages until a consumer pulls and deletes them, up to 14 days (default 4).

Visibility timeout is the clever bit: a message isn't deleted when read, only hidden. If the worker dies, it comes back. That's how SQS guarantees nothing is lost.

Four messaging services, four shapes

SNS

Push one message to many subscribers.

Use forAlerts, fan-out, SMS and email.

SQS

A buffer. One consumer handles each message.

Use forBackground jobs, absorbing spikes.

EventBridge

An event bus with routing rules and schedules.

Use for“When X happens anywhere, do Y.” SaaS events.

Kinesis

An ordered stream many readers can replay.

Use forClickstreams, real-time analytics.

Quick rule: notify many → SNS; do work later, safely → SQS; route events by content → EventBridge; high-volume ordered stream with replay → Kinesis.

Behind the scenes

Why a message can arrive twice

SQS stores each message redundantly on multiple servers across AZs so it survives failures. A side effect of that design: standard queues guarantee at-least-once delivery, so very occasionally a message is delivered twice.

Production rule: use an idempotency key (like order_id). Charging a customer twice is the classic bug.

Chapter 10

Packed tiffins on a private shelf

Kabir moves the app into Docker containers. Where do the images live, and how do they reach servers?

ECRECSEKS

Container image = the app plus everything it needs, packed like a tiffin box.

An image is a stack of layers

ubuntu base · 29 MB
python 3.12 · 48 MB
pip packages · 61 MB
your code · 2 MB

Change one line of code → only the top layer changes.

Push uploads 2 MB, not 140 MB. Servers pull only what they lack.

Each Dockerfile instruction makes a layer. Layers are identified by a hash of their content, so identical layers are stored and transferred once.

Behind the scenes

Tags move. Digests never do.

ECR stores image layers in S3 behind the scenes, which is where its durability comes from. A tag is a movable label; the digest is a content hash.

Extra features worth naming: image scanning for known vulnerabilities, lifecycle policies to delete old images, cross-Region replication.

Production: from git push to live in minutes

The amber dot travels the pipeline. Each stage lights up as it passes. If a health check fails after deploy, ECS can roll back automatically.

ECR vs Docker Hub: same concept, but ECR is private by default, controlled by IAM and sits in your Region.

A database with a manager on staff

The MySQL Kabir installed by hand needs backups, patches and a plan for 3 am failures.

RDSAURDDB

RDS = Relational Database Service. You run SQL; AWS runs the database server.

Hand the chores to AWS

Click: five chores slide to AWS. You keep the data model, queries, and access control. The trade-off: no SSH into the database server.

Engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, plus Aurora.

Insurance vs extra hands

Click 1: a read replica with asynchronous copy for dashboards. Click 2: the primary fails, and the endpoint DNS flips to the standby (typically within a minute or two). The app reconnects to the same name. Click 3: summary.

In classic Multi-AZ, the standby can't serve reads. Newer Multi-AZ DB clusters have readable standbys.

Behind the scenes

Aurora writes every change six times

6copies across 3 AZs
4 of 6must confirm a write
3 of 6enough to read

Lose a whole AZ: 4 copies left. Writes keep going.

Aurora separates compute from storage. The storage layer keeps six copies of your data across three AZs. A write is acknowledged when four of the six confirm; a read needs three. Losing an entire AZ (two copies) still leaves four, so writes continue; losing an AZ plus one more copy still allows reads.

Source: AWS's Aurora design paper (SIGMOD 2017) and Aurora documentation.

Which database?

RDS

Managed MySQL, PostgreSQL, MariaDB, Oracle, SQL Server.

Use forStandard relational apps. Most teams start here.

Aurora

MySQL/PostgreSQL-compatible, 6-copy storage, fast failover, up to 15 replicas.

Use forHigh availability and scale. Serverless option.

DynamoDB

NoSQL key-value. Single-digit-ms at any scale. No servers.

Use forCarts, sessions, huge simple lookups.

DB on EC2

You install and run everything yourself.

Use forUnsupported engines or settings. Rarely.

Rule of thumb: relational data with joins → RDS or Aurora. Massive key-based access with simple queries → DynamoDB.

An SG protects the whole subnet.
It's per instance. The NACL covers the subnet.
Replies need an outbound rule.

Private subnet = no internet at all.
Nothing comes in. Out is possible through NAT.
Stopped instances cost nothing.
EBS, snapshots and public IPs still bill.
S3 has real folders.
Flat store. “img/” is part of the key.
Multi-AZ doubles read capacity.
Classic standby isn't readable. Use replicas.
My AMI works in every Region.
AMIs are regional. Copy first.
