The lab way vs the enterprise way

Lab: easy to reach, easy to attack

  • Public access: Yes
  • Security group: 3306 from 0.0.0.0/0
  • Password typed into the docker command
docker run -p 80:3000 \
  -e DB_HOST=db.xxxx.rds.amazonaws.com \
  -e DB_PASSWORD=MySecret123 node-mysql-app

Enterprise: invisible from outside

  • Public access: No · private DB subnets in 2+ AZs
  • sg-db: 3306 only from sg-app
  • Password in Secrets Manager, rotated automatically
  • Multi-AZ on · automated backups · encryption at rest

The left column is exactly the PDF 09 lab: public access true, 3306 open to everywhere. It's the quickest way to learn, and the quickest way to get breached in production. Bots scan the internet for open 3306 constantly.

Aurora: MySQL and PostgreSQL, rebuilt for the cloud

5×throughput of standard MySQL (AWS claim)
3×throughput of standard PostgreSQL (AWS claim)
6copies of your data across 3 AZs
15read replicas, typically under 10 ms behind
Autostorage grows by itself as data grows
Automonitoring and failover

Figures from PDF 09, which match AWS's published Aurora claims. Throughput multiples are AWS benchmarks; real results depend on the workload.

Before vs after: one database vs primary + read replicas
What changed: 3 read replicas for search and dashboards, Multi-AZ for safety
Why not just run MySQL on EC2?
You can. But with RDS, backups, patching, failover and replicas become checkboxes instead of your weekends.
You trade SSH access to the database server for sleep. Most teams take that deal.

Add a column? Change every row. Joins across tables.

DynamoDB table · flexible items

{ "id": "1", "name": "Raju", "age": 25 }
{ "id": "2", "name": "Sham", "age": 28 }
{ "id": "3", "name": "Baburao", "age": 45,
  "garage": "Star Garage" }

Each item is a JSON-like document of key-value pairs. Only the key is required.

Ask by key, get an answer in single-digit milliseconds, at any scale.

The users table (Raju, Sham, Baburao) is straight from PDF 10. Yes, it's a Hera Pheri reference. Use it.

Behind the scenes

The secret: split the table into many small pieces

DynamoDB hashes the partition key to decide which partition holds an item. Partitions are spread across many storage nodes and replicated across AZs. That's why choosing a key with many distinct values matters: a "hot" key that every request uses would overload one partition.

Serverless, auto-scaling, global

Serverless

No servers, installs or patches. Zero downtime for maintenance.

PricingOn-demand: pay per read and write. Idle table costs nothing for requests.

DAX cache

In-memory cache built for DynamoDB. Microsecond reads, up to 10× faster.

Use forHot items read over and over.

Global tables

The same table replicated across Regions, writable everywhere.

Use forUsers in India and Europe both getting local speed.

Free tier: 25 GB of storage plus 25 read and 25 write capacity units, enough for roughly 200 million requests a month. Great for: mobile, web, gaming, ad tech, IoT.

From PDF 10. DAX works only with DynamoDB; ElastiCache works with other databases too. Free tier details can change, so check aws.amazon.com/free.

Before vs after: cart data in MySQL vs DynamoDB + DAX
What changed: moved seat-hold carts to DynamoDB, hot items cached in DAX
What database answers 151 million requests a second?
One that splits every table into partitions and only touches the one piece each request needs.
Use DynamoDB for huge, simple, key-based data. Use RDS when you need joins and complex queries. Many apps use both.

Bring the website closer to the user

TicketWave starts selling tickets for a world tour. The servers are in Mumbai. Fans in Stockholm say the site is slow.

CDNEDGE

Based on PDF 14 (AWS CloudFront).

Why does the same website load instantly in Mumbai but slowly in Stockholm?
Rahul, on a call with the Europe team
Same code, same server, same images. Only the distance changed.

Copy the heavy files to the corner shop

Step 1: CloudFront puts an edge location near Stockholm. The first request misses and fetches from Mumbai once. Step 2: every later request is served from the edge. Step 3: what gets cached (controlled by TTLs, cache behaviours and origin headers, per PDF 14).

Three places a file can be cached

No cache

Every user, every file, every time: all the way to the origin.

ResultSlow far away, origin overloaded on big days.

Browser cache

A mini-CDN on each device. Repeat visits are fast.

LimitOnly helps that one user, and only the second time.

CloudFront

Edge locations worldwide share one cached copy for everyone nearby.

ResultFast for first-time visitors too, origin barely touched.

PDF 14: browsers act like a mini-CDN by caching website files locally, but this only helps individual users.

Before vs after: origin only vs CloudFront in front
What changed: CloudFront distribution in front of S3 + ALB
Why is the site fast in Mumbai but slow in Stockholm?
Because light takes time. CloudFront moves the files to the user instead of moving the user to the files.
Same app, one config change: the site now loads like it's hosted in every city.
