Signboards decide everything

Public = 0.0.0.0/0 → igw. The name means nothing.

Private = no route from the internet. Out through NAT.

10.0.1.0/24

Every subnet has exactly one route table. Traffic for the VPC range stays local; everything else follows 0.0.0.0/0.

CIDR slider: /16 = 65,536 addresses, /24 = 256. AWS keeps 5 in every subnet: .0 network, .1 VPC router, .2 DNS, .3 reserved, and the last one (broadcast).

Five doors out of a VPC

Internet GW

Two-way door to the internet.

Use forPublic web servers, load balancers.

NAT gateway

Private servers go out. Nobody comes in.

Use forUpdates, calling outside APIs. Billed per hour + per GB.

Gateway endpoint

Private route to S3 and DynamoDB only.

Use forS3 traffic without NAT. Free.

Interface endpoint

A private IP in your subnet for an AWS service (PrivateLink).

Use forSSM, ECR, Secrets Manager from private subnets.

Egress-only IGW

NAT's idea, for IPv6.

Use forIPv6 servers that must not be reachable.

A common production cost surprise: private servers pulling large files from S3 through a NAT gateway pay NAT data-processing charges. A free gateway endpoint for S3 removes that.

Connecting many VPCs

Peering links grow as n×(n−1)/2: 10 VPCs need 45 peerings. Transit Gateway turns that into 10 attachments. PrivateLink shares just one endpoint service, even when CIDRs overlap.

Behind the scenes

Creating a VPC doesn't lay a single cable

Thousands of customers' VPCs share the same physical network, and many even use the same 10.0.x.x addresses. They never collide because every packet is wrapped (encapsulated) by the Nitro card with the physical address of the destination host, found through an internal mapping service.

The VPC router you see in route tables isn't a box anywhere; routing is implemented in every host. That's why a VPC is created in seconds.

This is described in AWS re:Invent networking talks about the VPC "Mapping Service"; details are simplified here.

The layout most production apps use

Three tiers, three AZs. Only the load balancer is public. App servers sit in private subnets and reach out via a NAT per AZ. The database is in isolated subnets with no internet route at all.

One NAT per AZ costs more than one shared NAT, but if one AZ fails, the others keep outbound access.

Custom NACLs must also allow replies on ports 1024–65535.

The amber reply is checked again at the subnet edge because the NACL has no memory. The security group lets it through without a check because it remembers.

Most teams leave the default NACL (allow all) and do everything with security groups.

Behind the scenes

There is no central firewall box

“Stateful” = a connection table.

Allowed connections get a row. Replies matching a row skip the rules.

Anything without a matching rule is dropped before it reaches your instance.

Security group rules are enforced at the host level on the Nitro system, outside your instance, so even root on the instance can't bypass them. Connection tracking is how "stateful" works.

Fun detail: SG rule changes apply to existing instances within seconds; no reboot.

Production: chain groups, not IPs

Each tier only accepts traffic from the security group of the tier in front of it. Scale from 2 to 200 app servers and no rule changes.

One physical server, many instances

Launch in about a minute. Pay per second. Gone when you terminate.

Linux instances are billed per second (60-second minimum) for most instance types.

Other suffixes: i = Intel, a = AMD, g = Graviton (AWS's own ARM chips, usually better price-performance), d = local NVMe disk, n = extra networking.

Sizes double each step: large → xlarge → 2xlarge, roughly twice the vCPU and memory each time.

Same server, four prices

Production mix: Savings Plans for the base, On-Demand for peaks, Spot for batch jobs.

Discounts are AWS's published maximums. Spot suits work that can be interrupted: CI builds, image processing, data jobs. Never run your only database on Spot.

Who manages what?

There's no "best"; there's a trade-off between control and operational effort. Lightsail is another option: simple fixed-price servers for small sites.

Behind the scenes

The card that changed EC2

Click 1: Nitro cards take networking, EBS storage and security off the host CPU. Your instance gets nearly all the host's resources, and bare-metal instance types become possible.

Click 2: by design, the Nitro System has no mechanism for anyone, including AWS staff, to log in to the host or read your instance's memory. AWS has published a whitepaper on this.

Behind the scenes

Your “hard disk” isn't inside your server

EBS is network storage that looks like a local disk.

Replicated inside one AZ, which is why a volume can only attach to instances in the same AZ.

Stop the instance and the disk survives. Snapshots copy it to S3 so it can move.

The blocks flying across are disk reads and writes travelling over the network to EBS storage servers. The Nitro EBS card makes this look like a local NVMe disk to your OS.

Instance store is physically attached to the host: very fast, but its data is lost when the instance stops or the host fails.

Production: servers that add themselves

Traffic rises → instances added. Falls → removed.

Launch template: which AMI, type, SG and role to use.

Load balancer: sends traffic only to healthy instances.

Health checks: a sick instance is terminated and replaced.

Stop vs terminate: stop keeps the disk; terminate deletes the instance.

Watch the CPU line rise past the target: instances appear in the group box. As load drops, they're removed. This is how ChaiCart survives next Diwali without anyone awake at 2 am.
