Security group vs IAM role

Rahul's server already has a security group. His lead says “attach a role too.” Isn't one lock enough?

SGIAM

The most common confusion for people new to AWS. We'll settle it with one picture, one console screen and three real examples.

Two locks. Two different questions.

Click 1: traffic coming IN to the server. The security group is a firewall: it only understands network things like ports, protocols and source IPs. It decides whether a packet may reach the server at all.

Click 2: calls going OUT from the server to AWS services. S3, SQS and Secrets Manager are not inside your VPC; they're AWS APIs. They don't care about your firewall. They ask: who are you, and are you allowed to do this action? The role answers that.

Click 3: the guard at the office gate decides if you can enter the building. Your employee ID card decides which systems you can use once you're in. You need both, and neither replaces the other.

Same instance, same tab, two different things.

Answer to the question “is the SG associated with the resource or with IAM?”: with the resource. Precisely, with its network interface (ENI). You create it in the VPC/EC2 console; IAM has nothing to do with it.

The role is created in IAM, but it's also attached to the resource: for EC2 through an “instance profile”, in the console under Actions › Security › Modify IAM role. Lambda calls it an execution role, ECS a task role.

People (Rahul, Neha) never get security groups. People get IAM users or SSO access; resources get roles and security groups.

Click 4: this is literally what you see on the instance's Security tab.

Example 1: the app can't upload a poster to S3

Start: the app calls S3's PutObject. The security group allows all outbound traffic, so the request reaches S3. S3 checks the caller's identity, finds no permission, and returns 403 AccessDenied.

Click 1: Rahul's first instinct: open more ports. It changes nothing, because S3 never sees or cares about your security group.

Click 2: attach a role whose policy allows s3:PutObject on that bucket. Same network, same SG. Now it works. The fix was identity, not network.

Example 2: the role is admin, the site still times out

The opposite mistake. The server's role is AdministratorAccess, the most powerful policy there is. Fans still can't open the site: the security group has no inbound rule for 443, so packets are silently dropped and the browser spins until it times out.

Click 1: add “443 from anywhere” and the page loads instantly. No IAM change was needed.

Click 2: the debugging rule of thumb. A timeout means the packet never arrived: look at the network (security group, NACL, route table). An AccessDenied message means it arrived and AWS said no: look at IAM.

Example 3: the app talks to RDS. Three gates.

Real enterprise flow. Click 1: the app fetches the DB password from Secrets Manager. That's an AWS API call, so the role must allow secretsmanager:GetSecretValue.

Click 2: the app opens a connection to RDS on port 3306. That's network, so sg-db must allow 3306 from sg-app.

Click 3: MySQL itself checks the username and password. That's the database's own login, neither IAM nor SG.

Click 4: each gate fails with a different error message. Read the error, and you know which gate to fix.
