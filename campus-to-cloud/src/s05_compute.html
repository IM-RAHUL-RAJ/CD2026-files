How do engineers actually pick an instance type?
They don't guess. They pick the family by bottleneck (CPU, memory, GPU), start small, and resize from real metrics.
t = bursty, m = balanced, c = compute, r = memory, g/p = GPU. Changing size is a two-minute stop-start, not a purchase.

Is the disk inside the server? Can I move it? Can I make it bigger without downtime?

A disk that outlives its server

Step 1: detach the volume. Step 2: the instance is terminated, the volume survives. Step 3: attach it to a new instance in the same AZ. Step 4: to move to another AZ or Region, take a snapshot and create a new volume from it. All straight from the PDF 05 diagrams.

Volumes can be resized live: no data loss, no restart needed.

Four flavours of disk

gp3 · gp2

General purpose SSD. Balances price and performance.

Use forBoot disks, most apps, dev databases.

io2 · io1

Provisioned IOPS SSD. You set the IOPS you need.

Use forBusy production databases.

st1

Throughput-optimized HDD. Big sequential reads.

Use forBig data, log processing.

sc1

Cold HDD. Cheapest per GB.

Use forData you rarely touch.

From PDF 05. EBS is AZ-specific, replicated within its AZ, supports encryption and snapshots, and can grow without downtime.

Before vs after: gp2 vs gp3 for a 100 GB database disk
What changed: switched the volume type, live, no downtime
If I terminate my instance, what happens to my data?
Your data lives on an EBS volume across the network, not inside the server. Detach it, keep it, or snapshot it anywhere.
Just remember the one default that bites: the root volume is deleted on termination unless you turn that off.

Three kinds of AMI

Public

Published for everyone: Amazon Linux, Ubuntu, Windows.

Use forTesting, development, a clean starting point.

Private

Built by you, visible only to your account or accounts you share with.

Use forYour hardened, customized production setup.

Marketplace

Paid images from vendors, billed by usage.

Use forA ready LAMP stack, firewalls, enterprise software.

From PDF 06. Marketplace example in the PDF: a pre-configured LAMP stack, so you skip installing Apache, MySQL and PHP by hand.

Clean the server before you photograph it

#!/bin/bash
# remove SSH keys
rm -rf ~/.ssh/authorized_keys
# clear credentials and history
rm -rf ~/.aws/credentials ~/.git-credentials ~/.bash_history
# clean logs and temp files
rm -rf /var/log/* /tmp/* /var/tmp/*
# remove temporary users, lock root
deluser tempuser --remove-home
passwd -l root

An AMI copies everything: apps, configs, users, and any secret you forgot.

Bake a key into an image and every one of its 50 copies has it too. Clean first, then create the image.

Cleanup script from PDF 06 (lightly tidied). Real teams automate this inside EC2 Image Builder or Packer so nobody forgets a step.
