Same server, two ways to share it

Left: every VM carries a whole guest OS. Right: containers share one host kernel and carry only the app and its libraries.

Start them up

A VM boots an operating system: about a minute. A container just starts a process: under a second.

How many fit?

3 VMs fill this server. The same server runs 20 containers, because nobody is paying for 20 copies of an OS.

The trade-off

VMs have separate kernels: the strongest walls. Containers share one kernel: lighter walls, which is why AWS runs containers inside VMs (or Firecracker microVMs).

Step 0: point at the guest OS blocks: each VM has its own full OS, gigabytes each. Step 1: the boot race. Step 2: density. Step 3: isolation trade-off. In AWS you usually get both: containers running inside EC2 VMs, or on Fargate, which wraps each task in its own microVM.

Behind the scenes

A container is a flat in an apartment building

The building's foundation and utilities are the Linux kernel: every flat shares them. Each flat (container) gets its own door number (hostname), postal address (IP and ports), rooms (filesystem from the image), closed curtains (it can't see other containers' processes) and an electricity meter (a CPU and memory limit).

The technical names, for those who ask: namespaces give the separate view; cgroups are the meter. A VM is a whole separate house with its own foundation (its own kernel): stronger separation, more cost.

What really happens when you type docker run

Click through the chain. The docker command is only a client: it sends a REST call to dockerd. dockerd asks containerd to run the container; containerd uses runc, which asks the kernel to create a process with new namespaces and cgroups, mounts the image layers with overlayfs, then exits.

Click 2: if the image isn't on this machine, dockerd pulls its layers from the registry first. Click 4: networking and port publishing.

Line by line

A real Dockerfile

A multi-stage Dockerfile for a Spring Boot service. Two stages: a big one to build the jar, a small one to run it. Click through line by line.

Step 1

FROM … AS build

Start a temporary build kitchen with Maven and JDK 21. Name it build so we can copy from it later. Versions are pinned: 3.9, 21, never latest.

Step 2

pom.xml first, then dependencies

Copy only pom.xml and download every dependency. Docker caches this layer, so it only re-runs when pom.xml changes. Editing code no longer re-downloads the internet.

Step 3

Then the code

Copy the source and build orders.jar. Tests already ran in CI, so we skip them here to keep the build fast.

Step 4

A fresh, small base

Stage 2 starts clean from a small runtime: just the Java 21 JRE on Alpine Linux. Maven, the JDK and your source code are left behind in stage 1.

Step 5

Don’t run as root

Create a normal user and switch to it. If someone breaks into the app, they are not root inside the container.

Step 6

Carry only the jar

COPY --from=build takes just the finished jar out of the build stage. That’s the whole trick of multi-stage builds.

Step 7

Port, health, start

EXPOSE documents the port. HEALTHCHECK lets Docker ask Spring’s /actuator/health. ENTRYPOINT starts Java as PID 1.

Walk the seven steps. The two ideas that matter most: dependency caching (copy pom.xml before src, so the slow dependency download is a cached layer) and multi-stage builds (build with the big toolbox, ship only the jar on a small runtime).

Build it: docker build -t orders:1.4.2 . Run it: docker run -d -p 8080:8080 orders:1.4.2. Sizes are approximate.

Tag every image like a release

A tag is a name you give an image: repository:tag. Version every build (semantic version plus the git commit), and pin base images to a specific version so your build doesn't change under you.

Click 1 and 2: each new build gets its own version tag, and the latest tag jumps forward. Click 3: the four rules teams follow. We'll see in the ECR chapter why trusting latest in production bites.

Each Dockerfile line adds one read-only layer, stacked like glass sheets. Each layer is named by the hash of its contents.

docker push

Each layer is compressed (tar + gzip): 207 MB becomes 74 MB, and travels to the registry separately.

docker pull on a server

The server already has the python base: Already exists. Only the missing layers download, then unpack.

docker run ×3

Three containers share the same image on disk. Each gets a thin writable layer. Change a file and it's copied up first: copy-on-write.

Step 0: layers build bottom-up, one per instruction that changes files. Order matters: put things that change rarely (base, dependencies) at the bottom, your code at the top, so rebuilds reuse cached layers.

Step 1: layers are compressed tarballs, stored by their sha256 digest. Step 2: pulls skip layers you already have, which is why the second pull of a new version takes seconds. Step 3: the image never changes. Writes go to each container's own thin layer (overlayfs copy-on-write) and vanish when the container is removed, unless you use a volume.

Tip: logs without going in

Anything the app prints to the console, docker logs shows from outside. Use exec when you need the container's own files or tools.

docker exec runs a new command inside an already-running container. The three everyday reasons: read files the app writes (logs, config), use tools that only exist in that image (kafka scripts, psql, redis-cli), and test the network from the container's point of view (wget, nslookup).

The story: logs show a payment timeout; Kafka confirms the event was published; the database shows the order stuck in PENDING. Three containers, three tools, one root cause: payments. Typing exit leaves the shell; the container keeps running.

The plan

Four services in one file. Nothing is running yet: just the EC2 host.

docker compose up

Compose builds a walled network region and starts every service inside it. Inside the wall, every service can reach every other by its name.

From outside: one door

Your browser opens localhost:3000. The published port 3000:80 is the only door in the wall. It leads to frontend on port 80.

Inside: service to service

frontend → backend:8080 → postgres:5432 and kafka:9092. Names, not IPs, and no published ports needed.

Doors you didn't open

backend, postgres and kafka publish no ports, so from outside the wall they can't be reached.

docker compose down

Containers and the network disappear. The pgdata and kafkadata volumes stay on the host's disk.

Step 1: compose up creates one network for the project (named shop_default) and attaches every service to it. Step 2: the outside world only gets in through published ports; here only frontend publishes 3000:80. Step 3: inside the network, Docker's built-in DNS turns service names into container IPs, which is why config says postgres:5432. Step 4: everything else stays private. Step 5: down removes containers and the network; named volumes survive unless you add -v.

Volumes: where postgres and kafka keep their data

Click 1: without a volume, postgres writes into the container's own writable layer. Click 2: docker compose down (or replacing the container to upgrade) deletes that layer and the data with it.

Click 3: with a volume, the folder postgres writes to (/var/lib/postgresql/data) is really a folder Docker keeps on the host disk. Click 4: delete the container, start a newer postgres image, mount the same volume: everything is still there. Click 5: Kafka works the same way. Careful with down -v, which deletes named volumes too.

Activity · debug itTwo Node.js containers on one EC2. orders-api calls users-api every 3 seconds.

orders-api can't reach users-api. Why?

They ran orders-api with:

-e USERS_URL=http://localhost:3001

$ docker logs orders-api

ERROR connect ECONNREFUSED 127.0.0.1:3001

What is wrong?

Inside a container, localhost means the container itself. orders-api is calling its own port 3001, where nothing is listening.

USERS_URL=http://users-api:3001

They ran orders-api with:

-e USERS_URL=http://users-api:3001

$ docker logs orders-api

ERROR getaddrinfo ENOTFOUND users-api

What is wrong?

The default bridge network has no name lookup. Containers find each other by name only on a network you create.

docker network create shop-net
docker network connect shop-net users-api
docker run … --network shop-net …

They ran orders-api with:

--network shop-net -e USERS_URL=http://users-api:3001

$ docker logs orders-api

ERROR connect ECONNREFUSED 172.18.0.2:3001

What is wrong?

The name works now (it found 172.18.0.2), but 3001 is the host’s port. Inside the network, use the container’s own port: 3000.

USERS_URL=http://users-api:3000

They ran orders-api with:

--network shop-net -e USERS_URL=http://users-api:3000

$ docker logs orders-api

OK users: [rahul, ramya]

Same network, container name, container port. We found every bug with docker logs orders-api, and tested by hand with docker exec -it orders-api sh → wget -qO- http://users-api:3000.

Run it as a guessing game: show the command and the log line, let the room shout the cause, then Reveal. Each round is a real mistake people make in their first week with Docker.

Round 1: localhost inside a container is the container. Round 2: the default bridge has no DNS for container names; user-defined networks (and Compose) do. Round 3: published host ports (-p 3001:3000) are for the outside world; container-to-container traffic uses the container port. The next slide is the hands-on version for their EC2 machines.

docker network ls
