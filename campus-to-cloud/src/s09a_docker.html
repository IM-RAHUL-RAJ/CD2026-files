Same server, two ways to share it

Left: every VM carries a whole guest OS. Right: containers share one host kernel and carry only the app and its libraries.

Start them up

A VM boots an operating system: about a minute. A container just starts a process: under a second.

How many fit?

3 VMs fill this server. The same server runs 20 containers, because nobody is paying for 20 copies of an OS.

The trade-off

VMs have separate kernels: the strongest walls. Containers share one kernel: lighter walls, which is why AWS runs containers inside VMs (or Firecracker microVMs).

Step 0: point at the guest OS blocks: each VM has its own full OS, gigabytes each. Step 1: the boot race. Step 2: density. Step 3: isolation trade-off. In AWS you usually get both: containers running inside EC2 VMs, or on Fargate, which wraps each task in its own microVM.

No guest OS. Same kernel, different view.

Click 1: the six Linux namespaces. PID: the app sees itself as PID 1 and nothing else. NET: its own network interface and ports. MNT: its own root filesystem, built from the image. UTS: its own hostname. IPC: its own shared memory. USER: can map root inside to an unprivileged user outside.

Click 2: cgroups (control groups) limit memory and CPU. docker run --memory 512m --cpus 0.5 sets exactly these. Go over the memory limit and the kernel kills the process (OOMKilled).

Click 3: that's all a container is. Which is why it starts in milliseconds.

Behind the scenes

What really happens when you type docker run

Click through the chain. The docker command is only a client: it sends a REST call to dockerd. dockerd asks containerd to run the container; containerd uses runc, which asks the kernel to create a process with new namespaces and cgroups, mounts the image layers with overlayfs, then exits.

Click 2: if the image isn't on this machine, dockerd pulls its layers from the registry first. Click 4: networking and port publishing. Click 5: a small containerd-shim stays as the container's parent, so you can restart dockerd without killing running containers.

Recipe → frozen meal → hot plate

# Dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 8080
CMD ["python", "app.py"]

Dockerfile = recipe. Image = the frozen, versioned result of following the recipe. Container = a running instance of the image. One image can run as many containers.

The RDS labs in the PDFs use exactly this: docker pull, then docker run with -p and -e flags.

Each Dockerfile line adds one read-only layer, stacked like glass sheets. Each layer is named by the hash of its contents.

docker push

Each layer is compressed (tar + gzip): 207 MB becomes 74 MB, and travels to the registry separately.

docker pull on a server

The server already has the python base: Already exists. Only the missing layers download, then unpack.

docker run ×3

Three containers share the same image on disk. Each gets a thin writable layer. Change a file and it's copied up first: copy-on-write.

Step 0: layers build bottom-up, one per instruction that changes files. Order matters: put things that change rarely (base, dependencies) at the bottom, your code at the top, so rebuilds reuse cached layers.

Step 1: layers are compressed tarballs, stored by their sha256 digest. Step 2: pulls skip layers you already have, which is why the second pull of a new version takes seconds. Step 3: the image never changes. Writes go to each container's own thin layer (overlayfs copy-on-write) and vanish when the container is removed, unless you use a volume.

Three containers, one kernel

From outside, they're just boxes sitting on the host's Linux kernel.

docker exec -it api sh

Step through the walls. A whole new world spins up around you: its own processes, files, network and name.

ps: only 3 processes

Your app is PID 1. The host's hundreds of processes are invisible. That's the PID namespace.

ls /: a different root

This filesystem is the image layers plus a writable layer, not the host's disk.

Its own name and IP

Hostname 3f2a9c1b, its own eth0, cabled to a virtual bridge.

Look down

The floor is glass. Underneath is the same kernel as the host. The walls are just namespaces.

exit

Your shell ends. The container keeps running, because PID 1 (the app) is still alive.

This is the “aha” slide. docker exec starts a new process (sh) inside the existing container's namespaces, so you see exactly what the app sees.

Walk the steps: ps shows the app as PID 1; ls / shows the image's filesystem; hostname and eth0 come from the UTS and NET namespaces; uname -r shows the host kernel version because there is no guest OS. Exit ends sh only. If PID 1 dies, the whole container stops.

One file, the whole stack

Four services, one volume. Nothing is running yet: just your laptop.

docker compose up

Compose creates a private network ticketwave_default, then starts containers in depends_on order: db and redis, then api, then web.

Names are addresses

api asks the network's built-in DNS: “where is db?” → 172.18.0.4. Code just says db:5432.

You come in through one door

Browser → localhost:8080 → web:80 → api → redis and db. Only web has a published port.

Outsiders can't reach db

db has no published port, so from outside the network it doesn't exist.

docker compose down

Containers and network are removed. The db-data volume stays, so your data survives the next up.

Left panel highlights the part of compose.yaml that matters at each step.

Step 1: one command creates a network and starts services in dependency order. Step 2: every service name becomes a DNS name on that network (Docker's embedded DNS at 127.0.0.11), which is why config says db:5432 instead of an IP. Step 3: only ports you publish (8080:80) are reachable from your laptop. Step 4: everything else stays private to the network. Step 5: down removes containers and the network but keeps named volumes (unless you add -v).
