Bots scan public repos for leaked keys constantly. Deleting the commit later isn't enough: it's still in the history.

No one pushes straight to main

Branch protection on main means nothing merges without a pull request, passing checks, and approvals. Every check you see here runs automatically on every PR.

The pyramid: lots of fast unit tests at the bottom, fewer integration tests, a handful of slow end-to-end tests at the top.

Secret scanning with push protection would have stopped Rahul's college config.py from ever being pushed. If a secret does leak: rotate it first, then clean history. Deleting the commit alone doesn't help.

SonarQube (or SonarCloud) analyses code for bugs, vulnerabilities, code smells, coverage and duplication. The quality gate turns that into pass or fail, and Jenkins aborts the pipeline on failure.

Six security checks, placed along the pipeline

SAST reads your source code. SCA checks the libraries you depend on. Container scanning checks the OS packages in your image. IaC scanning checks your CloudFormation or Terraform for risky settings. DAST attacks the running app from outside, like a hacker would.

Before: in the code

AWS Secrets Manager

Managed, IAM-controlled, automatic rotation for RDS and others. Paid per secret.

Pick whenYou're on AWS and want rotation built in.

HashiCorp Vault

Multi-cloud, self-hosted or managed. Dynamic secrets: a DB password created per app, per hour.

Pick whenMany clouds, on-prem, advanced policies.

SSM Parameter Store

Simple key-value config, SecureString encrypted with KMS. Standard tier is free.

Pick whenConfig values and simple secrets, no rotation needed.

The app's IAM role decides which secrets it may read. In Kubernetes, the Secrets Store CSI driver or External Secrets Operator can sync from Secrets Manager or Vault into pods.

Before vs after: find bugs in prod vs in the pull request
What changed: secret scanning, SonarQube gate, SCA and image scans on every PR
How do companies stop passwords ending up on GitHub?
They make it impossible to push one, and they never put one in code to begin with: apps fetch secrets at runtime using their role.
Protected branches, bot reviewers and secret stores turn “please be careful” into “the system won't let you”.

CI, continuous delivery, continuous deployment

CI: integrate and test every change. Continuous delivery: every change could go to prod, but a human approves. Continuous deployment: no human gate; good automated checks decide. Most enterprises (especially fintech) use continuous delivery with an approval gate for prod.

Jenkins: a controller, many agents, one Jenkinsfile

pipeline {
  agent { label 'docker' }
  stages {
    stage('Build')  { steps { sh 'mvn -B package' } }
    stage('Test')   { steps { sh 'mvn test' } }
    stage('Scan')   { steps { sh 'trivy image tw-api:$BUILD_NUMBER' } }
    stage('Push')   { steps { sh './push-to-ecr.sh' } }
    stage('Deploy UAT') {
      steps { sh 'helm upgrade --install api ./chart -f values-uat.yaml' }
    }
    stage('Approve') { steps { input 'Ship to prod?' } }
    stage('Deploy prod') {
      steps { sh 'helm upgrade api ./chart -f values-prod.yaml' }
    }
  }
}

The Jenkinsfile lives in the repo, so the pipeline is versioned and reviewed like code. Agents can be EC2 instances or short-lived Kubernetes pods.

Jenkins, GitHub Actions, CodePipeline

Jenkins

Open source, self-hosted, 1,000s of plugins. Runs anywhere, including on-prem.

Pick whenComplex enterprise pipelines, full control. You maintain the servers.

GitHub Actions

YAML workflows next to the code. Hosted runners. OIDC to assume AWS roles without keys.

Pick whenCode is on GitHub and you want zero CI servers.

AWS CodePipeline

AWS-native pipeline with CodeBuild and CodeDeploy. IAM everywhere.

Pick whenEverything is on AWS and you want it managed.

Jenkins is still very common in Indian enterprises; GitHub Actions and GitLab CI are common in newer teams. The concepts are identical: stages, agents, artifacts, approvals.

Before vs after: manual releases vs a pipeline
What changed: Jenkins pipeline with tests, scans, Helm deploys and an approval gate
What happens between git push and users seeing my change?
A pipeline: build → test → scan → package → deploy to UAT → approve → deploy to prod. Same steps, every time, no SSH.
Small changes shipped often are safer than big changes shipped rarely, because when something breaks, you know exactly what changed.
Why can't we just test directly in production? Wouldn't that be more realistic?
Rahul, waiting two days for UAT sign-off

Four rooms before the stage

Names vary by company: QA is often called SIT (system integration testing), pre-prod is often called staging. The rules don't: one artifact promoted forward, config per environment, and real customer data only in production.

Why can't we just test in production?
Because prod holds real money and real data. Each room before it catches a different kind of mistake, cheaply.
And when teams do “test in prod”, they use the safe tricks you'll see next: canaries and feature flags.

Changing the engine mid-flight

A ticket sale is live. Rahul's fix must go out now. Nobody can be logged out, and no payment can fail.

How do big apps ship updates every day without users ever noticing?
Rahul, who once took FestPass down for an hour to fix a typo

Rolling and blue/green, side by side

Rolling update

Replace a few pods at a time. Old and new run together briefly.

Blue/green

Run a full copy of v2 next to v1, then flip all traffic at once.

Rolling: Kubernetes Deployments do this by default (maxSurge and maxUnavailable control the pace). Blue/green: two full environments; the load balancer or DNS flips. Rollback is flipping back.

Activity 5

Release a canary

Send a small slice of real traffic to v2. If error rates rise, roll back automatically before most users notice.

Try 5% → 25% → 50% → 100%. Then switch on the bug and try again.

Guardrail

If the error rate goes above 1%, roll back to 0% automatically.

Tools

Argo Rollouts, Flagger, AWS CodeDeploy, App Mesh or ALB weighted target groups.

Out of 2 million fans, 5% is 100,000 people. With the bug on, the guardrail rolls back at the first step: only the canary slice saw errors, for a minute. That's the point of canaries.

Feature flags add one more layer: ship the code switched off, then turn it on for 1% of users, then everyone. Rollback is flipping a switch, no deploy needed.

Real teams combine these: rolling deploys for most services, canaries for checkout and payments, feature flags for product changes, and helm rollback or kubectl rollout undo as the emergency button.

Before vs after: “maintenance window” vs canary + rollback
What changed: rolling by default, canary for payments, automated rollback
How do big apps ship daily without users noticing?
They never switch everyone at once. They roll, flip or canary, watch the metrics, and roll back in seconds if anything looks wrong.
A deploy stops being an event and becomes routine. That's the goal.
