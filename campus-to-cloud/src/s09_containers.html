TicketWave has 60 services. Each build makes a new image. Where do thousands of images live, safely?

Behind the scenes

Three versions, but shared layers are stored once

Each layer is stored by its content hash (sha256), so identical layers are stored once, no matter how many images use them. Only the top layer (your jar) changes between releases. That's why pushes and pulls of a new version take seconds, and why storage stays small.

This works best when your Dockerfile puts rarely-changing things (base, dependencies) at the bottom, as in the Spring Boot example.

A tag is a sticky note. A digest is a fingerprint.

A tag is a sticky note: a name you can peel off and stick somewhere else. A digest (sha256) is a fingerprint of the image's exact contents: it can never point at anything else.

Click through Monday, Tuesday, Wednesday. This exact surprise (a restart pulling a new latest) causes real outages. Fix: deploy exact version tags or digests, and switch on ECR tag immutability so 1.4.1 can never be overwritten.

How images flow through ECR

The pipeline pushes, ECR scans, lifecycle rules delete old images, tag immutability stops someone overwriting v3, and runtimes pull using IAM roles. Interface VPC endpoints let private subnets pull without a NAT gateway.

ECR vs JFrog Artifactory vs Docker Hub

Amazon ECR

Container images (and other OCI artifacts) inside your AWS account. IAM-controlled, in your Region, built-in scanning.

Pick whenYou deploy to AWS. Simplest, least to run.

JFrog Artifactory

Universal artifact store: Docker, Maven JARs, npm, PyPI, Helm charts and more. Cloud or self-hosted. Xray scanning.

Pick whenOne place for every artifact type, many clouds, on-prem too.

Docker Hub

The public default. Official base images like python, nginx, mysql. Private repos on paid plans.

Pick whenPulling public base images. Watch pull rate limits.

Many enterprises use Artifactory as the central store for everything (JARs, npm packages, images) and ECR close to the AWS runtimes. Both are valid; the choice depends on how many artifact types and platforms you have.

Inside the brain and the muscle

Control plane: API server (everything goes through it), etcd (stores desired state), scheduler (places pods), controller manager (runs loops that fix differences). Worker nodes: kubelet (starts pods and reports health) and kube-proxy (networking for services). In EKS, AWS runs and scales the control plane across multiple AZs; you manage (or let Auto Mode manage) the nodes.

Kubernetes in one picture: 2 services + 1 database

Click through the six layers.

1 Control plane: the brain. kubectl only ever talks to the API server; etcd stores what you asked for; the scheduler picks nodes; controllers keep fixing reality to match. 2 Worker nodes: EC2 machines. kubelet runs pods on its node, kube-proxy implements Services, containerd actually runs containers. 3 Pods, created by Deployments (stateless apps) and a StatefulSet (the database, with a stable name and its own disk). 4 Services: one stable name and IP for a changing group of pods. 5 Traffic: an Ingress becomes an AWS load balancer that sends users to the orders-api pods. 6 Helpers: ConfigMap and Secret become env vars, the HPA scales pods, a PVC gives postgres an EBS disk, and a Namespace fences the whole app.

Behind the scenes

Who routes user traffic to the pods?

Common confusion: “is it the API server that routes requests?” No. User traffic goes browser → AWS load balancer → pods. With target-type ip (our ingress.yaml), the ALB sends directly to pod IPs; the AWS Load Balancer Controller watches pods and updates the ALB target group as pods come and go.

Inside the cluster, pod-to-pod calls use a Service: a stable name and virtual IP, implemented on every node by kube-proxy. The API server only handles commands and status; if it went down for a minute, running apps would keep serving users.

Behind the scenes

What happens after kubectl apply

Nobody calls anybody directly: every component watches the API server and acts on what it sees. 1–2: your YAML is stored as the wanted state. 3: the Deployment controller sees missing pods and creates them. 4: the scheduler assigns each to a node. 5: the kubelet on that node starts the containers. 6–7: once ready, the pod joins the Service and the load balancer's targets. 8: the loop never stops; if anything drifts, controllers fix it. That's “self-healing”.

Drag the slider. The Horizontal Pod Autoscaler checks average CPU every 15 seconds: above 70% it adds pods, below it removes them (slowly, to avoid flapping). New pods land on nodes with room; when nodes are full, pods wait as Pending and the Cluster Autoscaler (or Karpenter on EKS) adds an EC2 node. When traffic drops, pods are removed, and empty nodes are removed too, so you stop paying for them.

order-service.yaml, explained

same template for all four services · click a note
apiVersion: apps/v1 1kind: Deployment spec: 2  replicas: 1 3  selector: { matchLabels: { app: order-service } }   template: 3    metadata: { labels: { app: order-service } }     spec:       containers: 4        - image: …ecr…/trading-order-service:3f9a2c1b7d0e 4          ports: [{ name: http, containerPort: 8081 }] 5          envFrom: 5            - configMapRef: { name: app-config } 5            - secretRef:    { name: app-secrets } 6          startupProbe:   { httpGet: /actuator/health } 6          readinessProbe: { httpGet: /actuator/health } 6          livenessProbe:  { httpGet: /actuator/health } 7          resources: 7            requests: { cpu: 100m, memory: 320Mi } 7            limits:   { cpu: 500m, memory: 768Mi } --- 8kind: Service 8spec: { type: ClusterIP, selector: { app: order-service }, 8        ports: [{ port: 8081, targetPort: http }] }
  1. 1Deployment: “always keep this pod running.” If it dies, a new one is made.
  2. 2replicas: how many copies. Change 1 to 3 and you have three pods behind one name.
  3. 3labels: the name tag on every pod. The Deployment and the Service find their pods by it.
  4. 4image + port: the image Jenkins pushed to ECR, tagged with the git commit.
  5. 5envFrom: every key of the ConfigMap and the Secret becomes an environment variable. Same as env_file: .env.
  6. 6three probes call /actuator/health: startup (wait for Spring to boot), readiness (send traffic only when ready), liveness (restart if stuck).
  7. 7resources: requests are the reserved seat the scheduler uses to pick a node; limits are the ceiling. Over the memory limit → OOMKilled.
  8. 8Service: a stable name, order-service:8081, inside the cluster, spreading requests over all matching pods.

Shortened from deploy/k8s-templates/app.yaml; apply.py fills in the name, image, port, health path and resources per service type (Java gets more memory than Node).

Key ideas: labels connect things; envFrom replaces env_file; probes replace the compose healthcheck and drive self-healing; requests and limits let the scheduler pack pods onto nodes safely.

Behind the scenes

Three questions Kubernetes keeps asking every pod

From app.yaml: startupProbe every 5 s with failureThreshold 60 (up to five minutes for a slow Java start), readinessProbe every 10 s, livenessProbe every 20 s, all on the health path. Readiness controls traffic (a pod that isn't ready gets no requests, which makes rolling updates safe); liveness controls restarts.
