Before shipping containers, every cargo was a puzzle

Click: the container packages the code with its runtime, libraries and OS files. The same box runs the same way on any machine with a container runtime. That's the whole idea behind Docker.

Containerization vs virtualization

Virtual machines

Each VM carries a whole OS. Boots in minutes. Strong isolation.

Containers

Containers share the host kernel. Start in seconds. Megabytes, not gigabytes.

In AWS you usually get both: containers running inside EC2 VMs, or on Fargate.

VMs virtualize hardware; containers virtualize the operating system. That's why containers are smaller and faster to start, while VMs give stronger isolation. Production often runs containers on VMs (EKS worker nodes are EC2 instances).

Recipe → frozen meal → hot plate

# Dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 8080
CMD ["python", "app.py"]

Dockerfile = recipe. Image = the frozen, versioned result of following the recipe. Container = a running instance of the image. One image can run as many containers.

The RDS and DynamoDB labs in the PDFs use exactly this: docker pull, then docker run with -p and -e flags.

Why does code break on someone else's machine?
Because you shipped the code but not its world. A container ships the code and its world together.
Same image on the laptop, in testing, and in production. If it ran once, it runs everywhere.

How images flow through ECR

The pipeline pushes, ECR scans, lifecycle rules delete old images, tag immutability stops someone overwriting v3, and runtimes pull using IAM roles. Interface VPC endpoints let private subnets pull without a NAT gateway.

ECR vs JFrog Artifactory vs Docker Hub

Amazon ECR

Container images (and other OCI artifacts) inside your AWS account. IAM-controlled, in your Region, built-in scanning.

Pick whenYou deploy to AWS. Simplest, least to run.

JFrog Artifactory

Universal artifact store: Docker, Maven JARs, npm, PyPI, Helm charts and more. Cloud or self-hosted. Xray scanning.

Pick whenOne place for every artifact type, many clouds, on-prem too.

Docker Hub

The public default. Official base images like python, nginx, mysql. Private repos on paid plans.

Pick whenPulling public base images. Watch pull rate limits.

Many enterprises use Artifactory as the central store for everything (JARs, npm packages, images) and ECR close to the AWS runtimes. Both are valid; the choice depends on how many artifact types and platforms you have.

Where do companies keep thousands of images?
In a private registry (ECR or Artifactory) where every image is scanned, versioned by digest, and pulled only by roles allowed to.
The image that passed tests is byte-for-byte the image that runs in prod. The sha256 digest proves it.

ECS in three words: cluster, service, task

Terms from the ECS PDF: cluster (group of tasks and services, hosts the infrastructure), service (handles scaling and load balancing), task (your running containers).

Run ECS on your servers, or on none

ECS on EC2

You run a fleet of EC2 instances; ECS places tasks on them. You patch and scale the fleet.

Pick whenSteady heavy load, GPUs, special instance types, lowest cost at scale.

ECS on Fargate

No instances at all. Say “0.5 vCPU, 1 GB” per task; AWS finds the capacity. Each task runs in its own isolated microVM.

Pick whenSmall team, spiky load, you never want to patch a node.

Fargate runs on Firecracker microVMs, the same technology behind Lambda (see the Firecracker slide).

Who restarts containers at 3 am?
An orchestrator. You declare “keep 3 running”, and ECS keeps that promise forever, replacing anything that dies.
That idea, called desired state, is the heart of Kubernetes too. Which is where we're going next.

The cluster

A control plane (the brain) and worker nodes (the muscle). Each cube is a pod.

kubectl apply

“I want 9 pods of ticketwave-api.” The scheduler places them across nodes.

A node dies

Its pods are recreated on healthy nodes automatically. Nobody gets paged.

Ticket drop

The autoscaler adds pods, then adds a new node when the others are full.

Step through: cluster, deploy, self-heal, autoscale. From the EKS PDF: Kubernetes automates deployment, scaling and management of containerized apps; a cluster has a master (control plane) and worker nodes.

Inside the brain and the muscle

Control plane: API server (everything goes through it), etcd (stores desired state), scheduler (places pods), controller manager (runs loops that fix differences). Worker nodes: kubelet (starts pods and reports health) and kube-proxy (networking for services). In EKS, AWS runs and scales the control plane across multiple AZs; you manage (or let Auto Mode manage) the nodes.

Six words that unlock Kubernetes

Pod

Smallest unit: one or more containers sharing a network.

Deployment

“Keep 3 copies of v3 running.” Handles rollouts.

Service

A stable name and IP in front of changing pods.

Ingress

HTTP routing from outside: /api, /seats → services. One ALB for many apps.

Namespace

Folders for teams: payments, search, dev.

ConfigMap · Secret

Settings and passwords injected at runtime.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ticketwave-api
spec:
  replicas: 3
  selector:
    matchLabels: { app: ticketwave-api }
  template:
    metadata:
      labels: { app: ticketwave-api }
    spec:
      containers:
      - name: api
        image: 4821….ecr…/ticketwave-api:v3
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: 250m, memory: 256Mi }

The YAML says "keep three copies of this image running". kubectl apply -f deploy.yaml sends it to the API server, and the controllers make it true.

Helm: one chart, many environments

Helm is the package manager for Kubernetes. A chart is a bundle of templated YAML; values files fill in the blanks per environment. helm rollback returns to any previous release number in seconds.
