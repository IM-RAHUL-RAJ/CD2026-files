Regions nest AZs. AZs nest data centers.

39Regions. Pick one per workload: near users, legal rules, services, price.
3+AZs per Region, ≤100 km apart. Close enough for synchronous replication, far enough apart that a flood or fire stays in one.
EdgeHundreds of edge locations run CloudFront and Route 53 close to users.

Most services are regional: EC2, VPC, RDS, Lambda. A few are global: IAM, Route 53, CloudFront.

Why within 100 km? Light in fibre covers roughly 200 km per millisecond, so AZs can replicate synchronously, but they're far enough apart that one disaster doesn't hit two.

Five places your code can live

Region

A full set of AWS services in one geography.

Use forAlmost everything. Default choice.

AZ

Isolated data centers inside a Region.

Use forSpreading copies so one failure doesn't stop you.

Local Zone

A small extension of a Region inside a big city.

Use forSingle-digit-millisecond apps: gaming, live video.

Edge

CloudFront and Route 53 points of presence.

Use forCaching images and pages near users.

Outposts

AWS racks installed in your own building.

Use forData that must stay on-site, factories, low latency to local systems.

Freshers mostly need Region and AZ. Mention the other three so nobody is confused when they see them in the console.

Behind the scenes

Your “ap-south-1a” may not be my “ap-south-1a”

AZ names (ap-south-1a) are labels that can map to different physical AZs in different accounts. AZ IDs (aps1-az1) always mean the same physical AZ in every account.

Where it matters in production: two teams in different accounts who want their services in the same physical AZ for latency, or sharing subnets with AWS RAM.

Find yours: EC2 console → Settings, or the AWS CLI's describe-availability-zones command.

Behind the scenes

If the AWS console goes down, does your app?

Click once: the control plane fails. The data plane packets keep moving. AWS designs data planes to be "statically stable": they keep working with the last known configuration even if the control plane is unavailable.

Production lesson: don't make recovery depend on control-plane calls (like launching new instances) in the moment of an outage. Pre-provision enough capacity in each AZ.

Production rule: assume an AZ will fail

Click: AZ b fails, the load balancer stops sending traffic there. Click: the capacity maths. With 3 AZs each sized at 50% of peak, losing one still leaves 100%.

With only 2 AZs, each must hold 100% of peak, so 3 AZs is often cheaper for the same resilience.

Chapter 1

Who is allowed in?

ChaiCart hires two interns and a designer. Kabir won't share the master key with anyone.

ACCIAMROLESTS

IAM answers two questions on every single AWS request: who are you, and are you allowed?

An account is a plot with one master key

Click 1: the root key goes in the vault. Click 2: daily work uses an admin identity, ideally through IAM Identity Center.

Root is only for a short list of tasks: changing account settings, closing the account, some billing and recovery tasks.

Real companies run many accounts

An account is the strongest isolation boundary in AWS: separate resources, separate bill, separate blast radius. A broken dev account can't touch prod.

Service Control Policies (SCPs) set the maximum permissions for every account in an OU. They don't grant anything; they put a ceiling on what can be granted.

Every request passes two checks

Watch the request token stop at each gate. First: prove who you are (a password and MFA in the console, or a signature made with access keys from code). Second: do the policies allow this exact action on this exact resource?

"Version" is always "2012-10-17": it's the policy language version, not a date to update. ARN = Amazon Resource Name, the unique address of any resource.

Three questions, in this order

This simplified order explains most AccessDenied errors beginners hit. In real organisations, SCPs, permission boundaries and session policies can also limit access; we compare those next.

Four kinds of policy, four jobs

Identity-based

Attached to a user, group or role. “What can I do?”

Use forDay-to-day permissions.

Resource-based

Attached to the resource. “Who can touch me?”

Use forBucket policies, cross-account sharing.

SCP

Set by Organizations on accounts. Grants nothing; sets the ceiling.

Use forCompany-wide guardrails.

Permission boundary

A ceiling on one user or role, however many policies they get.

Use forLetting teams create roles safely.

Effective access = what every layer allows, minus any Deny.

Think of it as overlapping circles: the action must be allowed by the identity policy (or the resource policy), and must also sit inside the SCP and the permission boundary if they exist.

Behind the scenes

Your secret key never crosses the internet

Every AWS API call made with access keys is signed with Signature Version 4. The SDK hashes the request with your secret key and sends only the request plus the signature. AWS recomputes the signature with its own copy of the key and compares.

Changing any part of the request breaks the signature, and the timestamp stops someone replaying an old request later.

That's also why leaked secret keys are so dangerous: whoever has the key can make valid signatures.

A role is a badge that expires by itself

✗ Access key pasted in config.py

Leaks to GitHub. Bots scan for keys constantly.

✓ Role attached to the server

Short-lived keys, rotated automatically. Nothing to leak.

Two policies per role

Trust policy: who may wear the badge. Permission policy: what it opens.

The ring empties and refills: credentials expire and are reissued automatically by STS, the Security Token Service.

Roles show up everywhere: EC2 instance profiles, Lambda execution roles, cross-account access, SSO sign-ins and CI/CD.

Behind the scenes

Where does a server get its badge?

169.254.169.254 is a link-local address: requests to it are answered on the host itself by the instance metadata service (IMDS). The SDK finds the role's temporary credentials there automatically, which is why your code needs no keys at all.

IMDSv2 requires a PUT to get a session token before any read. That defeats server-side request forgery attacks, where an attacker tricks your app into fetching a URL for them. Require IMDSv2 on all new instances.

Which identity, when?

IAM user

Long-term password and keys.

Use forBreak-glass or legacy tools only.

Identity Center

Single sign-on for people across all accounts.

Use forEvery human, every day.

IAM role

Temporary credentials for anything that assumes it.

Use forEC2, Lambda, ECS, other accounts.

Access keys

Key ID + secret for code outside AWS.

Use forLast resort. Rotate, never commit.

In production

CI pipelines assume a role with a short-lived OIDC token. No AWS keys stored in GitHub at all.

Modern rule: people use Identity Center, machines use roles. Long-term access keys are the exception and should be rare.

GitHub Actions, GitLab and others support OIDC federation: the pipeline gets a signed token from its provider, AWS trusts that provider, and STS returns temporary keys for a role.
