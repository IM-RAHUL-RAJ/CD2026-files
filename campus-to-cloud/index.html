One machine, many computers

The cloud rents you “a server”. But nobody gets a whole physical machine. So what do you actually get?

Based on the "What is Virtualization" PDF.

From one OS per machine to many

Step 1: the classic stack: hardware, one OS, apps. Step 2: the hypervisor slices the hardware into virtual machines, each with its own OS. Step 3: they're fully isolated. A crash in one doesn't touch the others.

A hypervisor hands out slices of real hardware

These are the exact numbers from the virtualization PDF: an 8 GB / 100 GB host gives VM1 2 GB RAM and 20 GB disk, VM2 2 GB and 10 GB. The rest stays free for more VMs.

Nitro: the server hires helpers

Analogy: a chef (the CPU) used to cook AND take orders AND fetch from the storeroom AND guard the door. Nitro hires a waiter, a runner and a guard, so the chef only cooks.

Click 1: the grey cores that did AWS's own work (networking, disk, security, the hypervisor) move onto dedicated Nitro hardware. Your instances get practically the whole server. The 12-of-16 split is illustrative; before Nitro, the Xen hypervisor's management domain used part of every host.

Click 2: the job of each helper. Nitro started in 2017 with the C5 family; every new instance type since runs on it.

Behind the scenes

Follow one web request and one disk write

Click 1: a request from the internet never touches the host CPU first. The Nitro network card handles VPC routing and enforces your security group. That's why we'll say later that a security group is attached to the instance's network card.

Click 2: your “disk” is EBS. The Nitro EBS card presents it to the OS as a local NVMe disk, encrypts the blocks and sends them to EBS storage servers in the same AZ.

Click 3: the Nitro security chip verifies firmware at boot, and the system has no operator login: no SSH, no interactive access, even for AWS staff.

Example: Rahul clicks “Launch” on a t3.micro

Walk the four steps. Step 2 is the Nitro hypervisor. Step 3 is the Nitro network card: the instance's network interface (ENI) and its security group live here. Step 4 is the Nitro EBS card attaching the root volume.

Remember step 3. In the security group vs IAM role chapter, we'll see that the security group is attached to this network interface, while the IAM role is attached to the instance itself.

Behind the scenes

Creating a VPC doesn't lay a single cable

Thousands of customers' VPCs share the same physical network, and many even use the same 10.0.x.x addresses. They never collide because every packet is wrapped (encapsulated) by the Nitro card with the physical address of the destination host, found through an internal mapping service.

The VPC router you see in route tables isn't a box anywhere; routing is implemented in every host. That's why a VPC is created in seconds.

This is described in AWS re:Invent networking talks about the VPC "Mapping Service"; details are simplified here.

The layout most production apps use

Three tiers, three AZs. Only the load balancer is public. App servers sit in private subnets and reach out via a NAT per AZ. The database is in isolated subnets with no internet route at all.

One NAT per AZ costs more than one shared NAT, but if one AZ fails, the others keep outbound access.

Security group vs IAM role

Rahul's server already has a security group. His lead says “attach a role too.” Isn't one lock enough?

SGIAM

The most common confusion for people new to AWS. We'll settle it with one picture, one console screen and three real examples.

Two locks. Two different questions.

Click 1: traffic coming IN to the server. The security group is a firewall: it only understands network things like ports, protocols and source IPs. It decides whether a packet may reach the server at all.

Click 2: calls going OUT from the server to AWS services. S3, SQS and Secrets Manager are not inside your VPC; they're AWS APIs. They don't care about your firewall. They ask: who are you, and are you allowed to do this action? The role answers that.

Click 3: the guard at the office gate decides if you can enter the building. Your employee ID card decides which systems you can use once you're in. You need both, and neither replaces the other.

Both are attached to the resource

Same instance, same tab, two different things.

Answer to the question “is the SG associated with the resource or with IAM?”: with the resource. Precisely, with its network interface (ENI). You create it in the VPC/EC2 console; IAM has nothing to do with it.

The role is created in IAM, but it's also attached to the resource: for EC2 through an “instance profile”, in the console under Actions › Security › Modify IAM role. Lambda calls it an execution role, ECS a task role.

People (Rahul, Neha) never get security groups. People get IAM users or SSO access; resources get roles and security groups.

Click 4: this is literally what you see on the instance's Security tab.

Example 1: the app can't upload a poster to S3

Start: the app calls S3's PutObject. The security group allows all outbound traffic, so the request reaches S3. S3 checks the caller's identity, finds no permission, and returns 403 AccessDenied.

Click 1: Rahul's first instinct: open more ports. It changes nothing, because S3 never sees or cares about your security group.

Click 2: attach a role whose policy allows s3:PutObject on that bucket. Same network, same SG. Now it works. The fix was identity, not network.

Example 2: the role is admin, the site still times out

The opposite mistake. The server's role is AdministratorAccess, the most powerful policy there is. Fans still can't open the site: the security group has no inbound rule for 443, so packets are silently dropped and the browser spins until it times out.

Click 1: add “443 from anywhere” and the page loads instantly. No IAM change was needed.

Click 2: the debugging rule of thumb. A timeout means the packet never arrived: look at the network (security group, NACL, route table). An AccessDenied message means it arrived and AWS said no: look at IAM.

Example 3: the app talks to RDS. Three gates.

Real enterprise flow. Click 1: the app fetches the DB password from Secrets Manager. That's an AWS API call, so the role must allow secretsmanager:GetSecretValue.

Click 2: the app opens a connection to RDS on port 3306. That's network, so sg-db must allow 3306 from sg-app.

Click 3: MySQL itself checks the username and password. That's the database's own login, neither IAM nor SG.

Click 4: each gate fails with a different error message. Read the error, and you know which gate to fix.

The blocks flying across are disk reads and writes travelling over the network to EBS storage servers. The Nitro EBS card makes this look like a local NVMe disk to your OS.

A disk that outlives its server

Step 1: detach the volume. Step 2: the instance is terminated, the volume survives. Step 3: attach it to a new instance in the same AZ. Step 4: to move to another AZ or Region, take a snapshot and create a new volume from it. All straight from the PDF 05 diagrams.

Snapshot 1 copies every used block.

Why the database hides in a private subnet

Green dots: the only path. Fans reach the load balancer in the public subnet; it talks to app servers in a private subnet; only app servers talk to the database.

Click 1: the database has no public IP and its subnet has no route to the Internet Gateway, so an attacker on the internet has no address and no road. Bots scan the whole internet for open port 3306 all day.

Click 2: even inside the VPC, the database's security group only allows port 3306 from the app servers' security group. A random server in the VPC is dropped.

Writes go to one. Reads go to many.

Click 1: every write (book a seat, pay) goes through the writer endpoint to the one primary. One writer means no two servers fight over the same seat.

Click 2: reads go through the reader endpoint, which spreads them across read replicas. Add replicas when browsing gets heavy.

Click 3: the primary streams every change to the replicas, usually milliseconds behind (asynchronous). So right after booking, read “my booking” from the writer, not a replica.

Click 4: most apps read far more than they write, which is why this scales. RDS for MySQL and PostgreSQL and Aurora support up to 15 read replicas. The 90/10 split is illustrative.

Multi-AZ: a twin waiting in another building

The app only knows one name: the endpoint. Behind it, RDS keeps a standby copy in a different AZ, which is a separate data centre with its own power and network.

Click 1: synchronous replication. A write is confirmed only after it is safely in both AZs, so no committed booking is lost.

Click 2: AZ a fails. RDS flips the endpoint's DNS to the standby, which becomes the new primary.

Click 3: AWS documents failover as typically 60–120 seconds. Nobody changes config. Note: a classic Multi-AZ standby does not serve reads. It's insurance, not extra hands; read replicas are the extra hands.

A private library for images

TicketWave has 60 services. Each build makes a new image. Where do thousands of images live, safely?

ECRJFROGHUB
Behind the scenes

Three versions, but shared layers are stored once

Each layer is stored by its content hash (sha256), so identical layers are stored once, no matter how many images use them. Only the top layer (your jar) changes between releases. That's why pushes and pulls of a new version take seconds, and why storage stays small.

This works best when your Dockerfile puts rarely-changing things (base, dependencies) at the bottom, as in the Spring Boot example.

A tag is a sticky note. A digest is a fingerprint.

A tag is a sticky note: a name you can peel off and stick somewhere else. A digest (sha256) is a fingerprint of the image's exact contents: it can never point at anything else.

Click through Monday, Tuesday, Wednesday. This exact surprise (a restart pulling a new latest) causes real outages. Fix: deploy exact version tags or digests, and switch on ECR tag immutability so 1.4.1 can never be overwritten.

How images flow through ECR

The pipeline pushes, ECR scans, lifecycle rules delete old images, tag immutability stops someone overwriting v3, and runtimes pull using IAM roles. Interface VPC endpoints let private subnets pull without a NAT gateway.

GitHub keeps the recipe. ECR keeps the meal.

GitHub is where humans keep and review the recipe (code and Dockerfile). The pipeline cooks it into an image and pushes it to ECR, where machines collect the ready meal. You never deploy from GitHub directly, and you never edit code in ECR.

Many enterprises use Artifactory as the central store for everything (JARs, npm packages, images) and ECR close to the AWS runtimes. Both are valid; the choice depends on how many artifact types and platforms you have.

  agent { label 'docker' }

One request, three kinds of evidence

Metrics tell you something is wrong (latency went up). Logs tell you what happened (gateway timeouts). Traces tell you where (the payment gateway call took 690 of 820 ms). Together they're observability.

Watch four numbers, catch most problems

latency
182 ms

How slow? Watch p95/p99, not just the average.

traffic
8.2k rps

How much demand? Requests per second.

errors
0.4%

How often does it fail? 5xx, timeouts.

saturation
71% CPU

How full? CPU, memory, queue depth.

The four golden signals come from Google's SRE book. Alert on symptoms users feel (latency, errors), and use saturation to see trouble coming.

Prometheus collects. Grafana shows. Alertmanager shouts.

Prometheus pulls (scrapes) metrics from /metrics endpoints on a schedule and stores them as time series. Grafana queries Prometheus with PromQL and draws dashboards. Alertmanager routes alerts to pagers and chat. On AWS, Amazon Managed Service for Prometheus and Amazon Managed Grafana run these for you.
